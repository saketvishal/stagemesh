# StageMesh 0.6.34

StageMesh 0.6.34 closes the unchanged-candidate review loop observed on
Caventra task 138 and makes run-window failure reporting truthful. It also
strengthens zero-configuration contracts so an issue's explicit file scope and
the repository's aggregate npm check survive initialization.

## Unchanged candidates are not reviewed again

- A failed implementation or `no_implementation_change` result remains in
  IMPLEMENT. It no longer advances the unchanged candidate back to REVIEW.
- An adapter cannot bypass that rule by returning the already-recorded candidate
  SHA as a successful durable handoff; StageMesh records it as no change.
- The previous independent review and its findings stay authoritative until a
  provider produces a new candidate or separately bound evidence resolves the
  finding.
- A second remediation row for the same failed stage and candidate is activity,
  not progress, even after another stage or a cleared row intervenes. It cannot
  reset the bounded no-progress detector.
- Regression coverage proves that a no-op remediation creates neither another
  review nor duplicate findings on the same candidate.

## Infrastructure failures cannot report success

- Any task outcome classified as `infrastructure_failure` makes its wave fail.
- `run-window` therefore returns a stopped, nonzero result instead of printing
  `OK` when a child runner crashed or no implementation provider was available.
- Independent infrastructure failures may still be collected across tasks for
  diagnosis, but the final report cannot claim the window succeeded.

## Initialization keeps project-owned constraints

- When a root `package.json` defines an aggregate `check` script, a newly
  generated profile uses `npm run check` rather than the narrower `npm test`.
- Rerunning `stagemesh init` upgrades only the exact older StageMesh-generated
  npm-test profile. Handwritten or edited profiles remain untouched.
- Profile-generated task contracts preserve an explicit `Allowed files` list
  from the source issue, narrowing the project profile instead of replacing the
  issue scope with `**`.
- Repository-wide, absolute, parent-traversing, and unprovably contained glob
  scopes from source issues fail closed instead of widening generated access.
- An explicit init test command never rewrites an existing generated npm
  profile through the automatic aggregate-check upgrade path.

## Regression evidence

Synthetic failure-path tests cover the exact unchanged-candidate transition,
duplicate and alternating remediation lineage, same-SHA adapter handoff,
single-runner infrastructure failure, npm gate selection and upgrade, and
adversarial issue-scope preservation. The focused set passes on Windows.
Broader real-Git tests must use a short temporary root on Windows; the
Codex app's sandbox temp path exceeds Git-for-Windows' worktree environment
limit and fails before lifecycle assertions run.

Focused tests, package metadata, attribution validation, hosted Linux and
Windows regression, protected-main review, and public PyPI verification remain
required before publication.
