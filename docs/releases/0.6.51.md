# StageMesh 0.6.51

StageMesh 0.6.51 fixes the source lifecycle after a StageMesh-published pull
request is merged outside the active landing callback. A normal `run-window`
now reconciles that merge before selecting new coding work, even when no task
is eligible, and completes the corresponding GitHub issue once delivery is
proven.

## What changed

- StageMesh reads the recorded publication, pull request, current base branch,
  commit ancestry, and exact-head check runs before recording an observed
  external merge.
- If the merged PR head differs from the originally published head, the task
  candidate must still be an ancestor, the configured GitHub approval authority
  must be the merger, and every observed exact-head check run must be complete
  and successful.
- The observed merge is stored as a separate audit event. It does not rewrite
  the candidate, review evidence, or prior delivery history.
- GitHub source completion first removes StageMesh's stale
  `stagemesh:task-blocked` label, then posts the completion comment and closes
  the issue. Any failed step is recorded and retried without changing local task
  state.

## Safety and compatibility

- Unknown repositories, fork heads, wrong base branches, unmerged or open PRs,
  missing ancestry, unauthorized mergers, missing or failed checks, malformed
  GitHub responses, and merge commits absent from the current base all fail
  closed.
- Exact published heads reuse the StageMesh evidence already bound to that
  candidate. Changed heads receive the additional merger and hosted-check
  requirements above.
- PR-only remains the default. This release does not enable automatic merging
  or change Caventra application code.

## Acceptance coverage

Synthetic tests cover exact and changed merged heads, idempotent audit and issue
completion, startup reconciliation with no eligible coding work, protected
approval-authority wiring, stale-label cleanup, and the negative cases listed
above.
