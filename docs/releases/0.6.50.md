# StageMesh 0.6.50

StageMesh 0.6.50 fixes the review lifecycle exposed after 0.6.49 successfully
collected the missing browser states. A newer normal-review PASS now supersedes
that role's earlier failure, while the distinct adverse-review role remains a
separate required gate.

## What changed

- Review state is evaluated by role and chronology. An older normal-review
  failure is not treated as an adverse-review failure after a verified normal
  recheck passes.
- Exact-candidate browser capture and executed independent review-role PASS
  records count as meaningful capped-step progress. StageMesh no longer calls
  those completed lifecycle milestones an idle loop.
- A narrow upgrade repair recognizes the 0.6.49 false state: normal review
  passed, adverse review is pending, but the task was sent to IMPLEMENT and
  blocked by the step cap. It clears only that false remediation and synthetic
  fallback finding, restores REVIEW, and preserves the candidate and evidence.
- A genuinely failed adverse review remains sticky for the candidate and still
  requires replacement or explicit governed disposition.
- Live acceptance is capability-specific. An implementation-only failure no
  longer disqualifies a provider from a review capability that was not tested.
- Grok reviews receive the exact candidate patch through a temporary prompt
  file and use read-only tools. This avoids Windows command-length failures,
  prevents review-time edit/shell access, and accepts one terminal verdict
  after structured progress records without accepting contradictory output.
- Recovery reports tolerate older repair records that predate bounded-attempt
  fields instead of crashing while formatting the completed window.

## Safety and compatibility

- The repair requires an exact candidate and contract, an executed independent
  normal PASS newer than the failed review, the matching adverse-policy digest,
  the known false REVIEW remediation, and no unrelated open findings.
- Ambiguous or incomplete ledgers do not receive the repair.
- Caventra application code, validation gates, and review independence rules
  are unchanged. Provider routing changed only to keep untested capabilities
  unproven instead of inheriting a failure from a different capability.
- No operator `retry-task` is required for the recognized 0.6.49 state.

## Acceptance coverage

Synthetic regressions cover historical normal failure followed by normal PASS,
normal-to-adverse coordinator continuation, unavailable adverse-review
capacity, capability-specific provider readiness, multi-record structured
review output, large Windows prompt delivery, browser/review progress
milestones, and persisted false-block repair.

An isolated copy of the actual Caventra task 138 ledger completed end to end at
candidate `265f8c572800cbd8f3c8e864440fbdbdc79fccc7`: validation passed, Grok
supplied the distinct adverse-review PASS, integration completed, and the task
reached DONE. Publication and merging were disabled, and the production ledger
hash remained unchanged. The grouped regression then passed 336 tests on
