# StageMesh 0.6.33

StageMesh 0.6.33 fixes the recovery-state failure observed after Caventra task
138 received its first substantive independent review. Codex correctly returned
two findings and StageMesh persisted them, returned the task from REVIEW to
IMPLEMENT, and queued remediation. The step-cap detector then misclassified that
new handoff as another unchanged IMPLEMENT loop and blocked the task.

## Review findings continue into implementation

- A newly persisted failed-check remediation is meaningful progress exactly once,
  even when the lifecycle intentionally moves backward to IMPLEMENT on the same
  candidate.
- The step-cap streak resets when that handoff is created, so the next normal
  window can give the findings to an implementation provider without an operator
  running `diagnose` or `retry-task`.
- Repeated activity, repeated remediation, and equivalent failures still do not
  count as progress. The existing bounded loop stop remains enforced.

## Source refresh preserves real blocks

- An eligible GitHub issue refresh reopens a task only when StageMesh has an
  audited source-retirement record proving that the issue was previously closed
  or ineligible.
- A normal refresh no longer treats every BLOCKED task as newly source-eligible.
  Operational, policy, dependency, and human-decision blocks therefore remain
  stable until their own recovery path resolves them.
- Run-window summaries and ledger state no longer diverge because source refresh
  silently undid a block immediately after it was recorded.

## Regression evidence

Synthetic state-sequence coverage reproduces the exact transition from an
incomplete review to a substantive failed review with persisted remediation and
proves that an earlier unproductive step-cap streak is reset. A separate GitHub
source regression proves that an unrelated operational block remains blocked,
while the existing closed/relabelled issue tests continue to prove legitimate
source restoration. Existing repeated-loop tests continue to prove that two
unchanged capped runs stop safely.

Focused tests, package metadata checks, attribution validation, hosted Linux and
Windows regressions, protected-main review, and public PyPI verification remain
required before publication.
