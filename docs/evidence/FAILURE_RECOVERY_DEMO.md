# Failure-Recovery Demo

## Status: PROVEN, reproducible, offline

This document records a real, reproducible demonstration of StageMesh's
failure-recovery lifecycle: a worker crash is detected, the task is not
stranded, another worker resumes it, and the task reaches governed
completion through the same review and integration gates a normal
successful run would use.

It does not use or expose any Caventra data, private product logic, or real
provider credentials. The "AI worker" is a deterministic scripted stand-in
(`tests/_scripted_worker.py`) that speaks the same executor contract
(prompt on stdin, structured JSON result file) as a real coding-agent CLI,
so the demo runs offline in seconds and produces the same coordinator code
paths a real execution would.

## How to run it

```bash
python docs/evidence/failure_recovery_demo.py
```

This creates a throwaway git project in a temp directory, defines one
task, and runs the real `build_coordinator` CLI (`python -m
build_coordinator continue demo`) against it. The demo task's first
builder attempt is instructed to exit without producing a result
(`SCRIPTED_WORKER_CRASH`), simulating a crashed worker/provider process.
StageMesh's own crash detection and recovery — not the demo script —
is what resumes the task.

The script prints the full CLI JSON output, writes it to
`docs/evidence/failure_recovery_demo_output.json`, and prints a short
summary.

## Lifecycle claims this demo proves

- **A worker/process can be deliberately interrupted.** The first BUILDER
  execution for the demo task exits (return code 3) without ever writing
  a structured result file, exactly like a real crashed provider process
  would.
- **StageMesh detects the crash rather than hanging or silently
  dropping the task.** The execution is recorded with `status: LOST` in
  the coordinator's execution history — it is not stranded or ignored.
- **Another eligible worker resumes the task.** A second BUILDER
  execution is launched for the same task and completes with
  `status: SUCCEEDED`.
- **Deterministic validation and independent review run on the
  recovered work.** A REVIEWER execution runs after the successful
  builder attempt and completes with `status: SUCCEEDED`.
- **The task reaches governed completion**, not just "the last process
  exited 0": INTEGRATION runs after review and the task's final state is
  `DONE`.

## What this demo does *not* claim

- It does not expose or assert the exact reviewed/feature SHA the
  reviewer validated against — the `continue` command's summary JSON
  used here does not surface per-execution SHA fields at the top level
  (they live in the coordinator's internal event store, not in this
  CLI summary). This document does not claim SHA-pinned review evidence
  beyond what is shown above.
- It does not demonstrate real external provider execution (Codex/Claude
  CLIs) — see [`CODEX_ACCEPTANCE.md`](CODEX_ACCEPTANCE.md) for that
  evidence. This demo isolates the crash-recovery lifecycle using a
  deterministic scripted worker so it is reproducible without live
  provider credentials.
- It does not demonstrate multi-provider fallback routing.

## Reproducibility

This is not a one-off manual demonstration — `docs/evidence/failure_recovery_demo.py`
is a runnable script anyone can execute locally (`python
docs/evidence/failure_recovery_demo.py`, no network access or credentials
required) to regenerate this evidence themselves.
